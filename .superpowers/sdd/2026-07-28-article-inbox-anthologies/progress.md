Task 16: D1/N2 assessed, PARTIALLY closed, remainder deferred. Both reviews flagged a TOCTOU between the emptiness check and the removal in the A10 rollback path: `ArticleFetchedCloudBatchApplier` is a `nonisolated struct` with no lock, so a concurrent local save that has completed `AnthologyCoverStore.prepareManagedDirectory` but not yet reached `data.write` can have its just-created `Anthologies/<id>/` removed. Assessment found the reviewers understated it. There are two distinct races, not one. (a) DATA LOSS: if a cover lands between the listing and the removal, `FileManager.removeItem` deletes directory contents RECURSIVELY, destroying a durably-referenced cover written by another writer. (b) SPURIOUS FAILURE: if the directory is genuinely empty at removal time, the concurrent writer's `data.write` fails and surfaces `AnthologyCoverStore.Error.unsafeDestination`. Race (a) is closed here, narrowly and without restructuring, by replacing `removeItem` with `rmdir(2)`: a single syscall that removes only an empty directory and fails with ENOTEMPTY otherwise, so a cover that appears after the check survives. The emptiness check is deliberately retained ahead of it rather than folded into `rmdir`, because `rmdir` is governed by the PARENT's write permission and would therefore reclaim an unreadable-but-empty directory that the existing check correctly leaves alone.
